GitHub Actions na task/multiplatform-rework — 0.9.0 / 19

Opis dotyczy plików workflow w repozytorium, nie uruchamia publikacji.
Android ID: pl.ekim.multiplatform_fm1_flasher. APK 0.9.0 jest lokalnym buildem testowym.

ANDROID CI (.github/workflows/android-ci.yml)
Push na branch, pull request lub ręczne uruchomienie. JDK 17, SDK 36 i Build Tools 35.0.0.
Sprawdza wygenerowane zasoby, testy shared JVM i Android JVM, lint debug i assembleDebug.
Przechowuje android-checks z APK/raportami przez 14 dni. Nie testuje fizycznego FM-1,
nie publikuje GitHub Release, nie buduje Swift i nie wykonuje osobnego zestawu
instrumentacyjnego Androida.

PAGES (.github/workflows/pages.yml)
Buduje dokumentację i sprawdza linki na wszystkich branchach/PR oraz ręcznie.
Wdraża tylko spoza PR, z domyślnej gałęzi repozytorium. Push task/multiplatform-rework
zwykle sprawdza stronę bez wdrożenia. Dokumentacja brancha może różnić się od strony
publicznej. Komendy lokalne i strukturę opisuje poradnik Pages.

GOOGLE PLAY RELEASE (.github/workflows/google-play.yml) — KONFIGURACJA ORYGINAŁU
Uruchamiają go wysłane tagi v* lub ręczny dispatch. Ręczne pole publish domyślnie ma true.
Buduje podpisany AAB i może wysłać go na internal. Fastlane --package_name nadal wskazuje
pl.ekim.fm1_flasher, podczas gdy ten branch tworzy pl.ekim.multiplatform_fm1_flasher.
Nie jest to skonfigurowana ścieżka publikacji forka. Nie twórz tagu v0.9.0 tylko jako
etykiety lokalnego APK: wyzwalacz v* może rozpocząć workflow Play. Żaden workflow nie
ustanawia automatycznego tworzenia wydania GitHub Releases.

Gdy ustawiono FM1_RELEASE_TAG, Gradle wymaga v<versionName>. Przyszły prerelease GitHuba
wymaga świadomego wyboru tagu/commita i osobnego przesłania zweryfikowanych plików.
Sam tag nie dostosowuje konfiguracji Play. Oddziel przekazanie APK, odbiór właściciela
na sprzęcie i publikację.

GOOGLE PLAY PRODUCTION (.github/workflows/promote-production.yml)
Ręcznie przyjmuje dodatni version_code i promuje istniejący bundle z internal na
production. Także wskazuje oryginalny pl.ekim.fm1_flasher. Nie buduje nowego pakietu
i nie jest ścieżką promocji forka.

PODPISYWANIE — STAN KODU
Lokalny Gradle czyta ANDROID_KEYSTORE_FILE, ANDROID_KEYSTORE_PASSWORD,
ANDROID_KEY_ALIAS i ANDROID_KEY_PASSWORD. Bez konfiguracji klucza bundleRelease
pozostaje niepodpisany. Klucze i hasła trzymaj poza Git.
Workflow release używa środowiska google-play, ANDROID_KEYSTORE_BASE64 oraz sekretów
hasła/aliasu; publikacja wymaga również GOOGLE_PLAY_SERVICE_ACCOUNT_JSON.
Production używa google-play-production i sekretu konta serwisowego. Samo istnienie
konfiguracji nie potwierdza dostępu do konta, rejestracji pakietu, ciągłości podpisu
ani gotowości sklepowej.

PRZED DOSTOSOWANIEM PUBLIKACJI
Ustal docelowy ID, wpis sklepu, certyfikat i versionCode. Sprawdź oba package_name,
archiwalną receptę F-Droid, opisy/grafiki i aktualną politykę prywatności.
Dotychczasowe screenshoty pokazują wcześniejszy UI. Najpierw przeprowadź odbiór
sprzętowy i weryfikację testowego APK przez właściciela. Regeneracja dokumentów
nie zmienia workflow, sekretów ani ustawień sklepu.
