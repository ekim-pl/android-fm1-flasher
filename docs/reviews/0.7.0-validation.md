# FM-1 Flasher 0.7.0 implementation and validation

The implementation is `0.7.0-experimental`, versionCode 13. The release channel is GitHub prerelease; this is not a stable or Google Play release. This follows the review of 0.6.4 and uses the requested persistent **Settings → Experimental features** switch in both debug and release builds, rather than permanently excluding recovery from the release variant.

## Implemented corrections

- R1: ROM chip detection now reports the device path and JEDEC ID without modifying the selected MIDI instrument's compatibility. Manual selection requires an identified target.
- R2: a reconnected endpoint must report an OTA identity before stage-two commands/data. A regression test asserts that normal-mode reconnect receives only the identity query.
- R3: experimental features default to off. MIDI Logger navigation, chip detection and recovery controls are hidden; service entry points are guarded. Disabling stops reception and clears recovery plans. The setting cannot change while busy. Backups are retained.
- R4: artwork accepts only the Hub HTTPS origin, without credentials or nonstandard ports, including every redirect. Firmware/API traffic has its own explicit GitHub/CDN hosts. JSON depth and token-size limits run before parsing remote content.
- R5: corrupt catalog data no longer permanently poisons subsequent refresh attempts. Repair occurs when the daily request budget allows; fresh corruption does not bypass that budget. A corrupt catalog still blocks flashing until repaired, so a previously withdrawn package is not silently authorized.
- R6: damaged settings are retained as `settings.invalid`; usable packages remain listed, selection is reset and safe defaults enable offline mode.
- R7: artwork has one job per URL, a bounded queue, atomic disk replacement, corrupt-image refetch and a 24 MiB cache quota. Legacy disposable previews are removed on startup. Firmware and recovery backups are not evicted.
- R8: logger ports close before handover; queued decoding drains off the main thread. Logger restart waits for drain completion. This removes main-thread executor waits and their exception path.
- R9: requests have a 60-second total deadline across redirects/reads, interruption checks and a scheduled connection disconnect. The User-Agent uses the actual build version. No cancel-writing button is introduced.
- R10: release automation now requires a pinned external fixture archive and rejects skipped/failed fixture tests before signing/upload. Android CI adds API 34/36 instrumentation jobs. Fixture archive configuration is documented in `publication/github-actions.txt`; repository/environment variables have not been configured remotely.
- R11: test JSON-java is updated to 20260719 and site Markdown to 3.8.2. Gradle versions are locked and artifacts verified by SHA-256. A reusable OSV audit covers binary JVM artifacts plus Python/Ruby pins.

Additional changes include an atomic unresolved-flash journal, session/reconnect deadlines with wake-lock margin, main-thread operation completion before publishing idle, callback-based MIDI disconnect detection, incremental unique-byte progress, linear-time catalog update lookup, revision-aware logger snapshots, hidden-panel timer suppression and streamed log export. Protocol pacing and protected recovery ranges are unchanged.

## Validation

- 97 JVM tests passed with no skips using the official hash-verified V15 package and a catalog snapshot. V15 was fetched from the catalog's pinned official GitHub commit, not the Hub firmware mirror. This run did not include V16.
- Three instrumentation tests passed on the local Android 16/API 36 emulator: cold launch, USB PendingIntent delivery and persistent experimental-feature/service guards. API 34 is configured in CI but was not run locally.
- Debug and unsigned release APK builds passed. Both lint variants report zero errors; existing warnings and newly unused legacy strings remain.
- A build using an empty Gradle cache passed all 97 JVM tests, both APK variants, lint and instrumentation APK compilation. It exposed four missing metadata checksums, which were verified against Maven Central and added. Platform CI uses an explicit shared AVD directory for creation and startup.
- Two Python tests passed for archive hash/path handling and missing/skipped release report rejection. The fixture gate passed against the complete JVM run.
- The documentation generator and local link checks passed for 44 pages after updating Python Markdown.
- Emulator UI verification confirmed that experimental controls are hidden by default and appear after enabling the setting, then disappear again when disabled. The code also guards delayed actions at service admission.

## Remaining work and limits

Physical USB flashing/recovery on both chip types, a 30-minute multi-port MIDI stress test and before/after performance measurements still require their respective environments. Android 14 execution is covered by the platform CI job, whose result must be checked before publication. No hardware success or measured speedup is claimed. Compatibility between an initially connected custom OTA loader and an arbitrary package remains a protocol question; this change does not infer a new version-matching rule without hardware evidence.

The expanded OSV audit returns 101 package/advisory matches across 363 queried package versions, predominantly Gradle/Android tooling dependencies. Its raw results are in [the toolchain audit](0.7.0-toolchain-audit.txt). These are not 101 demonstrated APK vulnerabilities; the resolved APK runtime remains Kotlin stdlib, annotations and CommonMark. The audit exits nonzero, and the tooling matches are not silently suppressed. Upgrading the Android/Kotlin toolchain and qualifying exposure remains separate work; no global forced transitive-version overrides were introduced.

Dependency verification metadata was generated from the resolved artifacts and needs the normal checksum review before accepting future dependency updates. Host-specific binaries not exercised here may require separately reviewed hashes.

Further drawing allocation cleanup, release minification and broad UI indexing are deferred until profiling justifies them. Upstream catalog signatures require a separate trust/key-distribution design. Hardware acceptance from the original plan remains pending; publication status is recorded in GitHub Releases. The original review is retained as a historical baseline.
