Bez zmian FlasherService, FleetStore, OAuthManager, workflowów i wspólnego planu.

Mechanizm
- Callback zapisuje się w istniejącym SourceCredentialStore (Android Keystore,
  AES-GCM), przed wyczyszczeniem Intent.data. Nie trafia do savedInstanceState.
- Przyjęcie wymaga dokładnego redirect, pojedynczego zgodnego state i ważnego
  żądania PKCE. Błędny callback nie zastępuje poprawnego oczekującego wpisu.
- Jeden wpis na aktualne state; pierwszy callback wygrywa, duplikat nie zmienia
  kodu ani terminu. TTL pochodzi z pierwotnego żądania OAuth (10 minut), a nie
  z chwili dostarczenia/redelivery. Wygasły/nieaktualny wpis usuwany przy dispatch.
- Blokada procesu i claim state przed handoff zapobiegają powtórnemu dispatch
  przez odtworzoną Activity lub kolejne powiadomienia Service.
- Zaszyfrowany wpis zostaje do zużycia/wygaśnięcia state. Po utracie procesu
  przed zużyciem state nowy proces może go odzyskać. OAuthManager pozostaje
  ostateczną bramką PKCE/state/revision, zużywając state przed token request.
- Błędy magazynu w Activity mają stały komunikat auth_storage_error, bez
  logowania wyjątku, URI lub kodu. Intent jest czyszczony także po odrzuceniu
  callbacku i po błędzie magazynu; taki błąd wymaga ponownego logowania.

   testOriginalStateDeadlineAndInvalidRedirectCannotOverwriteCallback.

Ograniczenia
- Dokładnie jedna wymiana w sprawdzonych ścieżkach lifecycle; brak ponownej
  wymiany po zużyciu state. Nagłe zabicie procesu między zużyciem state a
  ukończeniem token request wymaga nowego logowania. Nie ma transakcji obejmującej
  serwer OAuth i lokalny storage, więc gwarancja zakończonej wymiany exactly-once
  przy dowolnej awarii procesu/sieci nie jest możliwa. Nie dodano auto-retry.
- Brak API34, rzeczywistego dostawcy OAuth, fizycznego telefonu i wymuszonej
  awarii dysku/Keystore. Testy logów sprawdzają UiState.logs, nie cały logcat.
- TTL jest sprawdzany przy użyciu magazynu; nie uruchamia osobnego timera,
  gdy aplikacja nie działa. Nieaktywny wygasły ciphertext może pozostać na dysku
  do następnego uruchomienia. Kopie zapasowe aplikacji są wyłączone w manifeście.
- Szyfrowany zapis jest synchroniczny (mały, pojedynczy callback); bez nowego
  job systemu, zależności i zmian kontraktu Service. Pozostaje istniejąca
  semantyka odmowy zadania przy offline/błędzie inicjalizacji biblioteki.
