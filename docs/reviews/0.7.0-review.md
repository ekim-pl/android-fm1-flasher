# FM-1 Flasher code and security review for 0.7.0

Reviewed on 2026-11-14 against commit `39edfe0`, version `0.6.4-experimental`, versionCode 12. The working tree was initially clean. This review changes documentation only. The implementation plan is in [the 0.7.0 plan](../plans/0.7.0.md).

The existing package validation and recovery write boundaries are strong foundations. A stable 0.7.0 should first fix device association and OTA stage validation, and explicitly control access to experimental recovery. Performance work should focus on artwork scheduling, MIDI monitoring and repeated work during transfers. No evidence of remote code execution or an unauthenticated exported flashing interface was found in the reviewed application code; this is not a security certification.

## Scope and verification

The review covered the 24 production Kotlin files, Android manifest and Gradle configuration, JVM and instrumentation tests, release/CI workflows, documentation generator, dependency declarations and Ruby lockfile. The bundled RAM loader binaries were checked as a trust boundary in their caller, not decompiled or independently audited.

Executed checks:

- `./gradlew --no-daemon :app:testDebugUnitTest :app:lintDebug :app:assembleDebug`: successful; initially reused existing outputs.
- A subsequent `:app:testDebugUnitTest --rerun-tasks` run rebuilt and executed the baseline suite: **84 discovered, 80 passed, 4 skipped, no failures**. Skips require `FM1_TEST_PACKAGES`, `FM1_TEST_CATALOG` or `FM1_RECOVERY_V15`.
- Debug lint: **0 errors, 31 warnings**. Largest groups: 11 `SetTextI18n`, 6 `DrawAllocation`; also an accessibility warning for the custom refresh list. Warnings are not all defects: technical logger terminology is intentionally English.
- Final baseline test rerun, `:app:lintRelease` and `:app:assembleRelease` also succeeded. Release lint reports **0 errors, 31 warnings**. The unsigned release APK contains both `mflr-loader` assets, confirming that these binaries are packaged outside debug builds.
- Three temporary JVM probes all passed, confirming the current behavior in R2, R4 and R5. They asserted the existing defects, not the intended fixed behavior, and were removed from application tests after review.
- Documentation build and link validation passed for **44 HTML pages** using the pinned dependency in an isolated temporary Python environment.
- Resolved release runtime dependencies: Kotlin stdlib 2.2.21, JetBrains annotations 13.0 and CommonMark 0.32.0. Maven `org.json` and JUnit are test dependencies only.
- OSV queries covered 118 package/version pairs: those runtime dependencies, direct test dependencies, Python Markdown and the 112 gem entries parsed from `Gemfile.lock`. Two packages matched advisories, discussed in R11. This was not a complete scan of Gradle plugin transitive dependencies, the JDK, Android OS or runner images.

No physical flash/recovery operation, device instrumentation run, signed release upload or hardware performance benchmark was performed. The current CI does not run the two instrumentation tests. README descriptions of earlier hardware/emulator checks are historical evidence, not new validation of this review.

## Findings requiring changes

P1 means a safety issue or stable-release blocker. P2 means a bounded security, reliability or responsiveness issue. Line references describe the reviewed commit. Each finding distinguishes observed behavior from a possible hardware consequence.

### R1 P1 Chip detection can authorize another connected instrument

Evidence: [FlasherService.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/FlasherService.kt#L194), [MainActivity.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/MainActivity.kt#L770), [Catalog.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/Catalog.kt#L9).

`detectChipStopped(device)` writes a global `state.chip` without associating the result with `device`. The UI only requires one matching ROM download device; other normal MIDI devices may still be attached and selected. Connect a newer-chip instrument A in MIDI mode, then detect an older-chip instrument B in ROM mode: B's `OLD` result becomes A's compatibility selection. An old-only package can then pass both UI and service compatibility checks for A. This follows directly from the code; physical reproduction was not attempted.

Fix: keep detection as a separate result with its USB endpoint and timestamp. Do not copy it into the selected MIDI target's compatibility state. Require explicit association/confirmation after switching the same physical instrument back into MIDI mode; an ephemeral USB path alone cannot prove continuity across re-enumeration. Reset confirmed compatibility on target replacement. Add a two-device regression proving that B's detected ID cannot authorize writing A.

### R2 P1 Reconnection does not require OTA mode before the write stage

Evidence: [FlashSession.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/FlashSession.kt#L60).

After the verification-stage restart, the check only compares `identify(link).baseModel` with `FM-1`. Both normal `FM-1_015` and `ota-FM-1_015` satisfy it. The session then sends another upgrade command and serves package bytes. A temporary fake-transport test confirmed that a normal-mode endpoint receives the command and data before its verification terminal is rejected. A manually selected wrong normal-mode FM-1, or a target that returned to normal mode unexpectedly, is therefore not rejected before update traffic begins. Device-side consequences depend on its firmware.

Fix: require a validated loader identity before serving stage two. Test normal mode, another model, malformed identity, unexpected terminal, no requests and the supported stock/custom loader identities. Define loader/package compatibility from observed protocol evidence; do not assume every stock loader version must equal the requested application version. Likewise, resuming from an initially connected loader needs an explicit compatibility rule rather than a model-only rule.

### R3 P1 Experimental recovery is present in release builds

Evidence: [app/build.gradle](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/build.gradle#L27), [FlasherPanel.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/FlasherPanel.kt#L28), [FlasherService.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/FlasherService.kt#L318).

The documentation describes debug experimental recovery and explicitly says physical USB recovery has not been validated. However, UI actions, service command dispatch and RAM loaders are in `main`, with no release feature guard. A release AAB includes the same recovery capability. This is a release-readiness issue, not an exported-service vulnerability: the service is non-exported and user confirmation exists.

For stable 0.7.0, disable recovery writes in the release variant until the hardware matrix passes, enforcing the decision in the service as well as the UI. Keep the experimental build available for controlled validation. If recovery is intentionally shipped, update the documentation and require the same hardware evidence before release.

### R4 P2 Catalog artwork can trigger requests to arbitrary HTTPS origins

Evidence: [Catalog.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/Catalog.kt#L62), [FirmwareArtwork.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/FirmwareArtwork.kt#L78), [Catalog.kt network redirects](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/Catalog.kt#L154).

`card` accepts any resolved URL beginning with `https://`. A probe confirmed acceptance of `https://untrusted.example/track`. Rendering the card fetches it automatically. Redirects also enforce only HTTPS, not origin. A malicious/compromised catalog or trusted redirect endpoint can cause tracking requests or requests to other HTTPS services reachable by the phone, subject to normal certificate validation. No application credential forwarding or response exfiltration was demonstrated.

Fix: give artwork an explicit origin policy, initially the Hub's documented image origin, and apply it at every redirect. Reject credentials and unexpected ports. Use a separate policy for GitHub firmware/CDN downloads so legitimate asset redirects still work. This reduces unnecessary network authority; it does not solve compromise of the trusted firmware catalog itself.

### R5 P2 A corrupt fresh catalog cannot repair itself through refresh

Evidence: [Catalog.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/Catalog.kt#L102).

`load()` returns `read(fetched, true)` before its network/fallback `try` whenever the timestamp is fresh. A probe with a fresh timestamp and truncated JSON throws immediately and performs no recovery. `cached()` also propagates parse errors. The refresh button repeatedly fails until the freshness window expires; a corrupt cached catalog can additionally prevent a local flash because the service reads it before loading local firmware.

Fix: classify missing, valid and corrupt cache states separately. Quarantine corrupt data, preserve the daily network-attempt budget, and present a specific repair/retry state. Do not silently convert a known withdrawn package into an allowed one when recovering metadata. Test truncated JSON, timestamp corruption, no network and a recent failed attempt.

The 24-hour request limit itself is intentional. The [Hub usage rules](https://thefirmwarehub.com/kb/) require at most one catalog read per day. Improve next-attempt/error messaging rather than adding an unconditional force-refresh bypass.

### R6 P2 Corrupt settings can make the existing library unusable

Evidence: [LocalLibrary.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/LocalLibrary.kt#L63), [FlasherService.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/FlasherService.kt#L222).

Unlike individual package records, `settings.json` has no recovery path. `publishLibrary()` reads settings before listing packages. Invalid settings abort startup publication; later settings-dependent actions keep failing, even when package bytes and records remain intact. Atomic writes reduce the likelihood but do not repair pre-existing corruption.

Fix: quarantine invalid settings and offer/recover safe defaults while still listing independently verified packages. Keep offline intent conservative when it cannot be recovered, and do not delete firmware or recovery backups. Add malformed/truncated settings tests and a migration fixture from 0.6.4.

### R7 P2 Artwork work and disk usage are not bounded as a whole

Evidence: [FirmwareArtwork.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/FirmwareArtwork.kt#L60).

The bitmap LRU is bounded, but `newFixedThreadPool(2)` uses an unbounded work queue. Rebinding an uncached URL enqueues duplicate downloads, with no in-flight deduplication or task-time cache recheck. Stale rows still perform network work. Disk files under persistent `filesDir/previews` have no total quota or eviction. A failed partial file remains present and is repeatedly decoded without repair. Two concurrent tasks may write the same file non-atomically.

Fix: one in-flight job per URL, bounded pending work, task-time cache checks, atomic cache replacement and a disk quota in `cacheDir`. Invalid cache entries should be removed and fetched once when allowed. Keep user firmware and verified recovery backups outside automatic eviction. Test rapid scrolling/rebinding, same URL in two views, corrupt images and offline mode.

### R8 P2 Stopping the MIDI logger can freeze or crash the main thread

Evidence: [MidiMonitor.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/MidiMonitor.kt#L132), [FlasherService.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/FlasherService.kt#L150).

`stop()` is called from main-thread lifecycle and action handlers. It waits up to two seconds, then another second for the worker. If termination still fails it throws; `onAppClosed()` and `onDestroy()` do not catch that failure. Under load this creates a responsiveness hazard and a conditional crash path. A three-second wait alone does not prove an ANR, and no device ANR was reproduced.

Fix: disable receivers and close ownership on the main thread, drain parsing asynchronously, then publish completion. Flashing must wait for a successful handover, not start while monitoring still owns ports. Ensure lifecycle cleanup cannot throw into the activity/service callback. Test a saturated queue, delayed worker and rapid stop/start/flash.

### R9 P2 Network calls have inactivity timeouts but no total deadline

Evidence: [Catalog.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/Catalog.kt#L154), [FlasherService.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/FlasherService.kt#L241).

The 20-second read timeout is renewed by incoming data. A very slow server can keep returning bytes below that threshold and occupy the single library worker for an impractically long time. Redirects restart connection/read budgets. During a download, `busy` also blocks offline switching and other library operations. Byte limits bound memory, not elapsed time.

Fix: impose a total monotonic deadline across redirects and reads, account for remaining time in socket timeouts, and support cancellation of downloads/artwork by disconnecting the active connection. Do not reuse download cancellation as a stop-writing operation. Test a slow trickle, redirect chain, stalled read and recovery of the UI after failure.

### R10 P2 Release tests silently omit real-package and recovery gates

Evidence: [RecoveryTest.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/test/java/pl/ekim/fm1_flasher/RecoveryTest.kt#L40), [android-ci.yml](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/.github/workflows/android-ci.yml#L30), [google-play.yml](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/.github/workflows/google-play.yml#L45).

The four fixture-dependent tests use assumptions; workflows do not provision those fixtures or fail on their absence. A green suite can therefore omit the real V15 region validation and full `Recovery.restore` scenarios. The two instrumentation tests only cover cold launch and immutable PendingIntent delivery; neither is run by these workflows, and neither tests service lifecycle/USB handover.

Fix: keep synthetic tests available everywhere, but add a release verification job with legally sourced, hash-verified fixtures and explicit non-skipped assertions. Make it impossible to publish a recovery-enabled release without this gate and hardware evidence. Add focused Android tests for lifecycle and transport ownership; do not mistake JVM Android stubs for platform validation.

### R11 P2 Known dependency advisories affect tooling and tests

`website/requirements.txt` pins Markdown 3.7. OSV matches **CVE-2025-69534 / GHSA-5wmx-573v-2qwq** (also PYSEC-2026-89, the same issue), a malformed-input parser exception fixed in 3.8.1. This project's exposure is its documentation build processing repository content, not a live public Markdown service. Update to a reviewed fixed release and rerun site/link checks. [Upstream report](https://github.com/Python-Markdown/markdown/issues/1534).

`app/build.gradle` pins test-only `org.json:json:20240303`. OSV matches **CVE-2026-59171 / GHSA-ghc9-756g-vrcv**, numeric-input resource exhaustion fixed in 20260719. Update the test dependency to a reviewed fixed version. The Android APK uses the platform `org.json`; this advisory does not establish that the platform implementation has the same bug. Add on-device adversarial JSON tests instead of claiming that changing the test dependency fixes production parsing. [Upstream advisory](https://github.com/stleary/JSON-java/security/advisories/GHSA-ghc9-756g-vrcv).

No OSV matches were returned for the three resolved APK runtime packages, JUnit or the queried gem versions on the review date. This is a database result, not proof that those components have no vulnerabilities. Gradle dependency verification/locking and a regular dependency audit would improve future detection; action references are already pinned to commit hashes and the Gradle distribution has a SHA-256 pin.

## Additional safety questions for validation

- **Service completion ordering:** `finishLibraryTask()` and flash/recovery cleanup expose `busy=false` before `stopSelf()` and foreground cleanup finish. A new main-thread action can race with cleanup on the worker. Serialize completion and operation admission; use operation/start identity where appropriate. Android lifecycle reproduction is still required before calling this a demonstrated crash. `connect()` also relies on binding lifetime instead of starting the service like other worker operations.
- **Whole-session deadline:** the 15-minute check applies inside `serve()`, while identification, pauses and reconnect waits can extend beyond it. The wake lock expires after 15 minutes. Establish a coherent time budget and safe phase boundaries; never turn a deadline into an automatic retry of a destructive write.
- **Crash recovery evidence:** regular MIDI flash status exists only in memory. Persist a small operation journal before update commands, with target/package/stage and an unresolved outcome after process death. Recovery already keeps backups and result files, but result replacement should be atomic; distinguish process-death resilience from guaranteed survival of device power loss (directory metadata is not explicitly synced).
- **Catalog trust:** hashes from an unsigned HTTPS catalog detect mismatched bytes, not a malicious catalog author who can replace both the URL and hash. Signatures/attestations require an upstream trust and key-distribution design. They are a future trust-model improvement, not an isolated checksum fix for 0.7.0.
- **Protocol completion:** `requests > 0` plus a terminal and final version response is weaker than full flash readback. Do not enforce full logical-byte coverage blindly: loaders can request only relevant package ranges. Keep the existing documented distinction between identity confirmation and byte verification.
- **Parser resource limits:** total network limits are useful, but field lengths and nesting depth need explicit adversarial tests against Android's JSON implementation. A StackOverflowError or out-of-memory condition is not caught by `catch (Exception)`; do not solve this with a blanket `catch (Throwable)`.

## Optimization opportunities

1. **Transfer progress:** [FlashSession.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/FlashSession.kt#L99) calls `BitSet.cardinality()` after every request, including verification where progress is not shown. Track newly covered bytes incrementally, preserving duplicate/out-of-order request behavior, and skip progress bookkeeping for the verification stage. Benchmark before altering wire timing; retain protocol sleeps until hardware evidence permits changes.
2. **MIDI liveness:** [AndroidMidi.kt](https://github.com/ekim-pl/android-fm1-flasher/blob/39edfe0/app/src/main/java/pl/ekim/fm1_flasher/AndroidMidi.kt#L92) enumerates system devices for every send and receive check. Prefer callback-maintained connection state, with explicit fresh enumeration at selection/reconnect boundaries. Preserve disconnect detection and race checks.
3. **Logger rendering/export:** the panel snapshots up to 5000 entries every 100 ms before checking revision and filters the full list on updates. `MidiLogSnapshot.export()` formats an entire buffer into a single String with per-byte formatting. Use revision-aware snapshots, avoid hidden-panel ticking, and stream export through a Writer. Preserve complete export independent of UI filters and show data-loss counters.
4. **Catalog updates:** `CatalogBrowser.updates()` searches the full catalog for each local package; row rendering also repeatedly searches lists. Build ID maps once per catalog/library revision, and avoid recomputing package updates on every recovery progress event. The current limit is small enough that a new database is unnecessary.
5. **Recovery progress/UI:** three full reads during preparation/write verification generate many status notifications and UI updates. Coalesce repeated percentages and unchanged labels, preserving stage changes and errors. This is a responsiveness optimization, not permission to skip verification reads.
6. **Drawing and release size:** reuse paths/gradients where dimensions and theme are unchanged to address `DrawAllocation`. Evaluate R8/resource shrinking only after correctness gates, with an actual release smoke test and APK size measurement. No performance gains are claimed without profiling.

## Safeguards to preserve

- HTTPS-only network transport, explicit redirects, byte caps and image dimension/downsampling checks.
- Non-exported service, non-exported USB callback receiver and immutable PendingIntents with a real permission recheck.
- Explicit target selection, protected sibling endpoints, conservative automatic reconnect and final identity check.
- SHA-256 revalidation before flashing, UFW header/list CRCs, bounded ranges and payload checks.
- Hash-derived local filenames, atomic package/record updates and old-package retention on failed download.
- Two identical complete recovery reads, pinned V15 package/region, known boot hashes, protected sector bounds, pre-write revalidation and per-sector plus final readback.
- Bounded MIDI input queues/log buffers and visible loss reporting.

## Release recommendation

Treat 0.7.0 as a safety and reliability release. Resolve R1 and R2, enforce the R3 release policy, address R4–R11, and complete the applicable hardware gates before removing the experimental status. Avoid changing OTA packet layout, protected recovery regions or firmware compatibility claims as part of performance cleanup.
