# FM-1 Flasher 0.7.0 implementation plan

Implementation update: code corrections and validation are recorded in [the implementation report](../reviews/0.7.0-validation.md). The requested settings opt-in supersedes the proposed release-only recovery guard. Hardware acceptance and publication remain pending.

This plan turns the [0.7.0 review](../reviews/0.7.0-review.md) into a bounded safety and reliability release. It starts from `0.6.4-experimental`, versionCode 12, commit `39edfe0`. No implementation or publication is performed by this plan.

Keep the existing native Android UI, single application module, file-backed library and protocol implementation. Extract small testable policies only where needed for device association, operation state and network boundaries. Do not introduce Compose, a database, a general workflow engine or a new networking framework solely for this release.

## Milestone 1 Device safety and release boundaries

Priority P1. Complete before optimization.

- **R1:** separate detected ROM chip information from compatibility explicitly confirmed for the selected MIDI target. Touch `UiState`, `detectChipStopped`, connect/disconnect handling, `FlasherPanel`, confirmation UI and translated strings. Ensure no ROM device can authorize another MIDI target.
- **R2:** validate loader mode after reconnect before sending stage-two upgrade/data. Add an explicit compatibility policy for initial-loader resume, supported stock loader behavior and custom loaders. Keep unknown combinations blocked until evidenced; avoid assuming application-version equality for every stock loader.
- **R3:** add a build-time experimental recovery policy and enforce it at both UI and service entry points. Default stable release builds to no recovery writes until the full hardware gate passes. Detection and backup availability should be explicitly documented, not inferred from a button label.
- Add focused regression tests for A/B device confusion, wrong-mode reconnect, wrong-model reconnect, disconnected targets, duplicate confirmation and a recovery intent in the stable variant. Assert **zero upgrade/data/erase/program commands** on rejected paths.

Acceptance: a normal-mode endpoint after the loader reconnect is rejected before traffic; old-only compatibility cannot leak between instruments; release behavior matches documentation and cannot be bypassed by an in-app direct service call.

## Milestone 2 Operation lifecycle and recovery evidence

Depends on milestone 1's ownership policy.

- Serialize operation admission and completion on the main thread. Finish foreground/start ownership cleanup before publishing idle. Prevent an old task from stopping a newly admitted operation; use an operation identifier and appropriate service start IDs only where needed.
- Make connect, detection and export lifetime explicit across rotation/unbinding. Preserve current rules: logger stops on backgrounding, flashing can continue in the foreground service, no automatic restart of a destructive operation after process death.
- **R8:** stop receiver intake immediately, drain the logger asynchronously and start flashing only after ownership is released. Surface stop failure without throwing from lifecycle callbacks.
- Define whole-session timing across identify, verify, reconnect, write and final identification. Keep wake-lock coverage consistent with that budget. A failed/expired session must report an unconfirmed result; never resend destructive commands automatically.
- Persist a small normal-flash journal containing package hash, target description, phase and terminal outcome. On restart, show an interrupted/unconfirmed session and safe next steps. Make recovery result-file replacement atomic. Keep existing backups intact.

Acceptance: rotation, background/foreground, delayed device-open callback, two rapid actions and process death do not transfer ownership unexpectedly or report success without evidence. A blocked logger never freezes the main thread while draining. A new operation survives completion of the prior task.

## Milestone 3 Network and storage resilience

- **R4:** define separate URL/redirect policies for Hub artwork and GitHub assets. Reject unexpected scheme/host/port/credentials at each hop. Confirm required GitHub CDN hosts with actual asset metadata before enforcing the list.
- **R9:** implement total monotonic request deadlines and explicit cancellation for non-destructive network operations. Account for redirects and slow reads. Keep protocol write cancellation out of this change.
- **R5:** represent valid, absent and corrupt catalog cache separately. Quarantine invalid data, retain daily request budgeting, and expose next permissible attempt plus a useful failure message. Preserve offline access to validated local packages under an explicit withdrawal policy.
- **R6:** recover corrupt settings independently of package enumeration. Preserve files, reset unsafe selections, retain conservative offline behavior and notify the user once.
- **R7:** deduplicate artwork jobs, bound pending tasks, recheck cache when a task starts, replace files atomically and evict previews under a defined disk quota. Use `cacheDir` for disposable artwork. Never evict firmware or recovery backups automatically.
- Use `BuildConfig.VERSION_NAME` or equivalent generated version data for the User-Agent; remove the stale `0.5.1` literal.

Acceptance: tests cover redirect escape, HTTPS downgrade, slow trickle, oversized/chunked responses, corrupt catalog/settings/image files, full disk/write failure, offline startup and repeated binding of the same image. Catalog requests remain within the provider's daily limit. Failed updates leave the prior package usable.

## Milestone 4 Measured performance improvements

Implement after milestones 1–3 so ownership and cancellation are stable.

- Incrementally count newly covered transfer bytes; exclude verification-stage progress work. Test duplicate, overlapping and out-of-order requests with unchanged responses.
- Replace repeated MIDI enumeration inside the transfer loop with callback-maintained liveness, retaining revalidation at safety boundaries.
- Make logger snapshots revision-aware, stop hidden-panel timers and stream export. Preserve bounded retention, lost-byte accounting, timestamps and filter-independent export.
- Cache catalog/library ID maps per data revision and avoid recalculating library UI for every transfer progress event.
- Coalesce progress notifications and reuse drawing allocations. Evaluate minification separately only if size measurements justify it.

Acceptance: record before/after CPU, allocation rate, frame responsiveness and export peak memory on the same device and input. Use the maximum supported package size, a 5000-entry synthetic catalog and bounded high-rate multi-port MIDI. No optimization may weaken input validation, backup durability, disconnect detection or final verification. Do not reduce the 10 ms/other protocol delays without hardware tests.

## Milestone 5 Dependencies and release automation

- **R11:** upgrade Python Markdown to a reviewed version at least 3.8.1 and test-only JSON-java to a reviewed version at least 20260719. Check current advisories again at implementation time. Regenerate/pin dependency hashes as appropriate; avoid unrelated major toolchain upgrades.
- Introduce Gradle dependency verification and reproducible version locking where supported. Audit dependency graph changes. Keep existing action commit pins and wrapper checksum.
- **R10:** add a distinct release fixture verification job. Obtain official V15/V16 and catalog fixtures from permitted sources, pin hashes, and fail the release gate when required fixtures/tests are skipped. Do not bundle manufacturer firmware in source or the APK.
- Run instrumentation tests on Android API 34 and 36, including new service/permission/rotation tests. The emulator validates platform lifecycle, not USB hardware.
- Preserve reports for debug and release lint, JVM tests, fixture checks, dependency audit and unsigned release smoke builds. Fix actionable accessibility warnings and changed-code lint warnings; document intentional technical-English strings instead of suppressing all lint.

Acceptance: CI distinguishes synthetic, fixture, platform and hardware results. A green production gate cannot silently mean that recovery fixtures were absent. Verify the stable release variant, not only debug.

## Milestone 6 Hardware acceptance

Use recoverable test units and a powered hub. Record phone model, Android build, chip ID, initial/target firmware hashes and outcome. Fault injection belongs on units reserved for this testing.

Required for normal flashing:

- OLD and NEW chips with packages explicitly compatible with each; reject old-only packages on NEW/UNKNOWN.
- At least one successful stock/custom transition on each supported chip, with verification-stage restart, loader-stage write, final restart and identity check.
- Multiple identical units: select the middle device, prove siblings receive no update traffic, and verify their firmware remains unchanged.
- One normal MIDI target plus another ROM-mode device: detection cannot change target compatibility.
- Wrong normal-mode reconnect, multiple candidate reconnects, permission denial and delayed permission; all fail safely before unauthorized traffic.
- Rotation, backgrounding, screen off, USB loss in each phase and process termination. Report unresolved outcome accurately; no automatic destructive resume.
- Thirty-minute multi-port logger stress, queue overflow, export, stop/start and transfer handover, with visible loss counters and responsive UI.

Required before enabling recovery writes in a stable build:

- Validate the RAM transport and both loader variants on physical hardware.
- Run backup/prepare/restore on both allowed chip IDs; match the V15 region hash, read back the complete flash and verify protected/unique data unchanged.
- Test an interrupted write and safe subsequent recovery, corrupted backup rejection, unknown boot/chip rejection and exported backup integrity.
- Confirm boot separately after readback. A verified byte write is not itself a successful application boot.

If recovery acceptance is incomplete, ship stable 0.7.0 with recovery writes disabled and retain a clearly labeled experimental build. Do not substitute simulated flash tests for physical USB verification.

## Milestone 7 Packaging and rollout

- Keep applicationId `pl.ekim.fm1_flasher` and the established signing identity so existing installations can update and retain data.
- Set `versionName` to `0.7.0` only for the accepted stable build. Use a new unused monotonically increasing `versionCode`: **13 is the next candidate in this checkout**, subject to checking already uploaded versions. Pre-release candidates consume their own codes.
- Add the matching changelog in `fastlane/metadata/android/en-US`, `pl-PL` and `zh-CN`. Update README, about files, website translations and publication metadata to describe actual feature availability and verification limits.
- Test an in-place upgrade from 0.6.4 with downloaded packages, favorites, offline mode and recovery backups. Preserve these files; old preview cache can be cleaned as disposable data. Reconfirm selected firmware before a write if migration changes compatibility state.
- Build/test the actual release variant, validate signing and artifact checksum, then publish to internal testing. Promote the same accepted AAB through the existing production workflow rather than rebuilding it.
- Use tag `v0.7.0` matching Gradle's existing release-tag guard. Publishing remains a separate release action, not part of this review.
- If regressions appear, halt rollout and release a fix with a higher versionCode. Do not rely on downgrading Android installations or automatically restoring instrument firmware.

## Completion criteria

All P1 findings are closed, R4–R11 have verified fixes, the release variant passes its own tests, fixture tests required for shipped features are not skipped, and the applicable hardware matrix is recorded. No known severe dependency issue remains unexplained in its actual exposure context. Retained limitations are documented in all user-facing languages.

Defer broad architecture changes, automatic firmware rollback, batch flashing, expansion of recovery address ranges and upstream catalog signatures to separate work. They are not necessary to deliver this correction-focused 0.7.0.
